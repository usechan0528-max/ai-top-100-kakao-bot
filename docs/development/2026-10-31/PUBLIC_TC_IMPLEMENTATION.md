# 공개 TC 우선순위 구현·검증

작업일2026-10-31. [계획](PUBLIC_TC_DEVELOPMENT_PLAN.md)·[원문15개/73항](../../sources/public-tcs/README.md). 이번 요청은 계획에 따른 실제 코드/런타임 구현·공개 TC 검증과 병행 채팅 충돌 방지다.

## 소유권과 구현

공유 저장소에서 액션 토큰/P0 채팅과 조율했다. 기존 환불29·이관35·회원연결·Worker/배포 변경을 덮어쓰지 않고 `src/customer-request-actions.mjs`, `src/public-tc-policy.mjs`, `tests/public-tc-requests.test.mjs`를 별도로 작성했다. 안정본 배포 완료 후 공유 연결을 담당 채팅과 조율한다. 이번 신규 기능의 배포는 요청/수행하지 않았다.

- API24: 대상 주문·상세주소·귀속·정책 검토, 성공한 주문/배송 조회 근거를 요구한다. 집하 이후/대상불일치/조회실패는 차단한다. 요청본문은 new_address 하나이며 대상 일치/SUBMITTED/접수번호/유효 date-time을 검증한다.
- API32: 주문 payment_refs와 결제 order_no/approval_no 연결, 승인·양수 결제액·알려진 현금/이체수단, 고객 발행구분/번호·기한 검토를 요구한다. 본문은 receipt_number 하나다. receipt_purpose는 내부 검토 인자이며 API 필드로 창작하지 않는다. BANK_TRANSFER는 병행 실제 L-05 조회 결과를 전달받아 허용한 값이다. 알 수 없는 결제수단은 차단한다.
- attachCustomerRequestActions: 현재 메시지 처리 메모리에 성공 조회를 보관하고 실패 재조회 시 관련 근거를 무효화한다. 새 인스턴스/TC에 이전 조회가 이월되지 않는다. 개인정보를 DB/일반 요약에 추가하지 않는다. 주문 선조회→배송 또는 결제 조회→접수→최종답변의4단계가 필요하다.
- 공통: 고정 호스트/TC 헤더, 모델 인자의 URL·TC 변경 금지, 응답16KiB 상한·UTF-8/JSON 검사·취소, 미실행 명시 오류와 결과불확실 분리, 자동 재시도 없음. 접수 결과에 주소/발행번호를 반환하지 않는다. 기존 쓰기 journal/불확실 차단을 사용한다.
- 정책: 대상확인·실제 증빙·발행구분 미확정,5사례 필수이관·부분성공, 당도보장 두 선택지, 가능문의와 실행동의 구분, 날짜 문맥·미확정 컷오프를 명시했다.

## 검증 수준

새 테스트24개(모듈22·Worker2): L-03/05의 공식 경로·인자·접수 결과와 부정 사례, 잘못된 대상·미확인·카드/알 수 없는 수단·취소결제·잘못된 날짜·응답초과필드·미실행·불확실·중복 재시도 차단, 실행별 근거 격리/실패 무효화, L-11/23/32/33/34의35 접수 경로·lane·사유를 모의 전송으로 검증했다. 기존 runAgent 및 실제 주문/결제/배송 읽기 어댑터를 결합한4단계 왕복도 포함한다. 느린 스트림 취소·응답크기 상한도 검증했다. 모델은 결정론적 대역이며 공식 서버에 쓰기하지 않았다.

전체247/247은 adapter/추가1검사 전 실행 결과다. 최종 통합 후 결과는 후속 기록으로 갱신한다. 실제 모델의15개 전체 대화/73항 충족·공식 평가 합격·실제 카카오 접수 성공과 구분한다.

## 미확정·남은 범위

모델 확인 플래그/policy_basis는 독립 인증이나 고객 발화의 기계적 증명이 아니다. 이번 구현은 기존 회원정책을 변경하지 않으며 발화→확인 상태의 신뢰성을 모두 해결했다고 하지 않는다. 상세주소 완전성과 기발행 여부·기한/발행구분 의미는 정책 검토가 남고,32의 실제 발행구분 전달규약은 미확정이다. 주문 귀속·대상 확인의 더 강한 서버 상태 설계는 후속 과제다.

수신 로그인 메타데이터의 신뢰, API 시각과 시나리오 시계 연결, 마감 동일시각 포함 여부, 부분환불 산식은 임의 확정하지 않는다. 영수증 알 수 없는 코드·근거부족은 추측 대신 확인 대상으로 남긴다. 이미지/음성 인입·음성 전사, 조회01/03/04/06/20 확장,28/33/25/27 등은 이번 신규 구현에 포함하지 않는다. API35의 기존 구현·정책과 실제 전체 사례 수행은 별도다.


공개 TC 범위: L-03/05는 신규 접수와 선조회 흐름의 모의 실행, L-11/23/32/33/34는 기존35 이관의 인자/접수 검증이다. 나머지8사례의 전체 기능·모델 대화 검증은 아직 수행하지 않았다. 특정 모델 답변을 하드코딩한 대역 테스트를 실제 모델 정확도 점수로 표시하지 않는다.


## 최종 로컬 통합 결과

공유 파일 소유권 인계 후 action-context에 attachCustomerRequestActions를 연결하고 기존 회원대조·member_lookup_status·누적3회 제한을 보존했다. canUseOrder는 쓰기 직전 최신 matchedMember와 캐시 주문을 다시 대조한다. business-policy가 PUBLIC_TC_POLICY를 실제 SYSTEM_POLICY에 포함하며 공식 과거 상담일과 기본일을 구분한다. Worker는 검증된 접수종류/번호/소득공제 또는 지출증빙 요청을 유지한다. 주소·발행번호는 접수 수집 배열에 남기지 않는다. 모델의 완료 오답은 실제 접수 안내로 교체한다.

최종 실행: START_DEV.cmd check 통과, 문법39파일·전체262/262·데모 성공. 신규24개 중 Worker2개는 실제 어댑터/등록/프롬프트 전달/응답포맷/32,000자 모델 요청 상한까지 모의 HTTP로 검사했다. 각4회 모델 결정으로07→11또는17→24또는32→최종답변 성공. 신호취소·크기제한·조회실패·회원대조변경·TC격리·불확실 재시도 방지를 포함한다. 테스트 데이터/결정론적 모델을 사용했으며 신규 공식 쓰기·유료 모델 요청은0회다.

이번 신규24/32는 **로컬 런타임에 연결됐으나 미배포**다. 다른 채팅의 기존 회원버전310aa7f6-9035-4c58-bf02-5db07236d3bb 배포와 실제 카카오 회원대조→목록→주문/배송 및 후속연결 유지 검증은 [별도 기록](MEMBER_KAKAO_VERIFICATION.md)을 따른다. 이를 이번24/32 실제 카카오 성공으로 확대하지 않는다. 기존29/35 작업은 보존했고 전체15개/73항 합격,28/33/25/27·멀티모달 구현은 남아 있다.
