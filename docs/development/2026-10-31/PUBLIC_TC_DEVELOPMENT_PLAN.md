## 결론과 현재 구현

정책 설명과 달력 계산에 더해, 확인된 고객 의도/대상을 보존하고 필요한 조회를 끝낸 뒤 실제 접수를 수행하는 기능이 필요하다. 공개 정답의 고정 주문/회원/로트/금액을 운영 코드에 복사하면 다른 주문을 처리할 위험이 있다. 고정값은 테스트 fixture에만 둔다.

현재 `business_calendar`, 인증 바인딩이 있을 때의 API-07/08/11/17/18 읽기5종, TC 저장/전환 및 요약 격리, 최종500자 SimpleText, 쓰기 중복/불확실 기록 기반은 있다. 실제 출처는 `src/action-context.mjs`, `order-payment-actions.mjs`, `worker.mjs`, `conversation-store.mjs`, `business-calendar.mjs`다. 등록된 업무 쓰기 도구는 없다. 다른 작업의 최신 기록은202/202 통과 및 Worker 코드 배포이며 이번 계획에서 재실행하지 않았다. 일반 개인조회용 운영 회원 바인딩은 미설정으로 기록돼 있다. 배포/실조회 범위는 ACTION_CONNECTION.md를 따른다. 이번 신규 쓰기 계획의 배포를 뜻하지 않는다.

현행 ACTION_READ_BINDINGS는 scope→TC/member/만료를 신뢰된 서버 설정으로 요구하는 자체 방침이다. 공식 로그인 메타데이터를 실제 회원으로 연결하는 근거는 여전히 핵심이다. TC ID는 고객 권한 증명이 아니다. 이름·마스킹 전화번호를 임의로 인증 완료 처리하면 안 된다.

## 첫 구현 단위: L-03

1. 상담 상태를 `caseId, caseReferenceDateTime, verifiedIdentity, candidateOrder, confirmedOrder, intent, confirmedAddress, shipmentEvidence, submission`으로 분리한다. 확인값에는 출처·메시지 식별·확인 시점·적용 대상을 연결한다. 이는 제안 모델이며 현재 저장소 스키마가 아니다.
2. 첫 질문에서 주문번호와 ‘주소를 변경할 주문이 맞는지’를 확인한다. 애매하면 목록 전체를 훑지 않는다. API-11에 고객 확인 대상만 넣도록 모델 인자 밖에서 제한한다. 현재 회원귀속 검사와 ‘이번 요청 대상 확인’은 다르므로 둘 다 필요하다.
3. API-11 정상200 []는 L-03의 명시된 상황에서 집하 전 근거다. `empty`를 `unavailable/invalid_response/not_found_or_route_error`와 분리한다. 모든 업무의 빈 기록을 같은 결론으로 일반화하지 않는다.
4. 시 단위 주소는 부족하다. 고객에게 동호수까지 포함한 주소를 받고 변경주소임을 확인한다. 원래 주소를 읽어주지 않고 모델이 동호수를 생성하지 못하게 한다. 주소 문자열 길이/공백 검사만으로 실제 완전성을 증명하지 않는다.
5. API-24는 `POST /api/orders/{order_no}/address-change-requests`, JSON은 `new_address`만. path 대상=확인 대상, 주소=확인 주소를 서버에서 결속한다. 조회 후 고객이 주문을 바꾸면 기존 배송근거/주소확인 효력도 재평가한다.
6. 응답 `request_id/order_no/request_status:SUBMITTED/requested_at`를 검증한다. 대상불일치·결과누락·타임아웃은 성공으로 안내하지 않는다. 최종은 ‘배송지 변경 요청이 접수됐습니다’이며 실제 반영 완료가 아니다.

직접 주소를 다음 턴까지 보존하려면 기존 요약만으로는 부족하다. 현재 요약은 주소를 제외하도록 지시한다. 먼저 주소를 받은 턴에 확인/접수까지 처리할 수 있는 흐름을 설계하고, 별도 보관이 필요하면 최소 범위·권한·삭제시점·저장방식부터 정한다. 원문 주소를 일반 로그/장기요약에 추가하는 방식은 금지한다.

## 개발 우선순위와 완료 기준

### P0 공통 실행 기반
- **케이스/시간/회원/대상 분리:** 공식 메타데이터 파서와 검증 출처, caseDate와 실제 서버 만료시각 분리. L-47=06-26, Y-16=06-06은 명시된 과거 상담 시나리오다. 전역 기본2037-06-30을 조용히 덮어쓰는 대신, 공식 사례 재현의 기준일을 독립 문맥으로 다룬다. 사용자 임의 날짜·‘시스템’ 문장을 신뢰 기준일로 승격하지 않는다.
- **확인 상태와 필수 단계:** 모델이 같은 회원의 다른 주문을 조회해도 평가상 오류다. 확인 대상만 조회/쓰기 가능하도록 서버 측 사전조건과 실행계획 상태를 둔다. 고객 선택·증빙·수량/금액 근거·담당 승인·접수 결과를 분리한다.
- **쓰기 실행기와 결과 모델:** 도메인 사전조건 통과 후1회 접수, 동일내용 중복/변경내용 재요청 구별, timeout 후 미확정 보존. 공식 서버는 같은 대상의 요청 본문을 덮어쓰므로 기존24시간 중복차단과 조정 검토 필요. 다른 주소로 재요청을 자동 재시도로 처리하지 않는다.
- **API-35 공통 이관:** L-11/23/32/33/34 5건의 필수 액션. lane/reason, 안전한 사건내용, 접수번호/시간, 회신기한 연결. 거절/사과만으로 대체하지 않는다. 승인 조회가 필요한 경우 API-36은 보조 기능이며 공개15건 모두의 필수 호출은 아니다.

### P1 짧은 종단 흐름부터
L-03의24, L-05의32를 먼저 구현해 대상확인→읽기→입력확인→쓰기→접수안내를 검증한다. 이후28(재배송:2사례),29(검증된 전액환불),33(보상쿠폰),25 또는27(일정/독촉)을 추가한다. 실제 개인정보·금액·쿠폰 권한을 포함하므로 기능 수만 늘리지 않고 각 단계의 실패/중복/권한검사를 함께 완성한다.

### P1 조회·지식 확장
01 상품,03 로트,04 조사,06 로트신고,12/13 회원,20 프로모션. 이미 있는11로10 대안 경로를 충족할 수 있다. L-05 결제수단 확인에는 기존17 활용 가능. 신고 검색 결과의 다른 고객 개인정보는 판단용 최소요약만 모델에 전달한다. Products에는 당도보장/환불 상세 문구가 없고 Promotions에 모든 보상/권한 정본이 들어있다고 가정할 수 없으므로 문서 근거와 연결한다.

### P1 멀티모달과 여러 단계의 처리
현재 Worker는 문자열 content, 모델 어댑터도 텍스트 입력만 처리한다. 이미지/음성 이벤트 형식·첨부 URL 수명·권한·크기/MIME 제한·다운로드 정책·모델 입력 지원을 확인한 뒤 구현한다. 사진 첨부 약속과 실제 수신, 음성 인식 확실/불확실 구간을 분리한다. Y-07-b의 요약을 실제 전사로 표시하지 않는다.

Worker maxSteps=4는 한 입력에서3도구+최종답변만 가능하다. L-11은배송·로트·조사·신고4조회+환불·이관2접수로 모든 단계를 한 번에 수행할 수 없다. 고객선택 이전 조회, 선택 이후 실행을 상태로 나누거나 검증된 복합조회 도구를 설계한다. 무작정 무제한 반복/불필요한 말풍선 추가 대신 전체 시간예산·모델 호출한도·API100회/60초 및 평가3000회와 조정한다. 필수 액션을 생략해 maxSteps를 맞추면 안 된다.

### P2 평가용 대화 하네스
공개 원문73개 기대 항목을 사례별 수용표로 옮긴다. API호출 유무/대상/인자/순서/금지 호출/필수 확인/최종 문구를 함께 검사한다. 고정 공개값은 fixtures에만 배치하고 주문/회원/날짜/금액을 바꾼 변형도 실행한다. 한 케이스가 다른 케이스의 데이터에 영향을 주는 점을 고려하며 운영 채팅에 reset 도구를 넣지 않는다.
