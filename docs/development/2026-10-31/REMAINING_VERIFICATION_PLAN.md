## 3. 실제 개발이 필요한 범위

### 이미지·음성 경로

확인 코드: `src/worker.mjs`의 identify/process, `src/openai-model.mjs`의 입력 구성. 현재 첨부 데이터를 판독·전사하는 경로는 확인되지 않았다. 입력 규격 확보 후 허용 형식·크기·접근 범위·만료·중복 이벤트를 처리하고, 첨부 안의 지시를 명령으로 실행하지 않도록 구분해야 한다. 사진의 배경 개인정보를 답변·요약에 불필요하게 남기지 않으며 판독하지 못한 내용을 확정하지 않는다. 새 경로의 비용·시간·누적 요청량도 기존 예산과 함께 확인한다.

### 새로 검수된 업무 규칙의 런타임 반영

`src/agent.mjs`는 BUSINESS_POLICY를, BUSINESS_POLICY는 PUBLIC_TC_POLICY를 포함한다. 새 [교차검수 가이드](../../prompts/SOURCE_CROSSCHECK_GUIDE.md)는 문서 반영 상태이며 자동으로 런타임에 주입되는 구조가 아니다. 다음을 개발 차이표로 먼저 다룬다.

- 판촉1개+보상1장+적립금 병용, 보상쿠폰의 발급 장수와 한 주문 사용 장수 구분. 계산 순서 미확정은 그대로 유지한다.
- 상품 표시 당도/중량 기준과 로트 최저값·검사 표본 범위를 대조. PHI 구역↔주문을 같은 생산자라는 이유로 연결하지 않기, 계획일을 실제 출고로 바꾸지 않기.
- 위탁 적재완료의 책임 경계와 고객창구 단일화, 내부 책임분담을 고객 구제 지연 사유로 사용하지 않기.
- 새 체험 자료의 문서상 조건과 현행 적용 미확정을 병기. 이미 확인불가 답변을 받은 질문을 다시 포괄 요구하지 않기.

쿠폰 쓰기는 현재 `src/fulfillment-request-actions.mjs`에서 CARE5000·단일SKU·수량1·주문금액=단가 조건으로 제한한다. 이는 L47의 지원 범위이지 확보한 전체 원장의 범용 구현이 아니다. CARE3000/10000 및 복수권종 발급 지원을 확대하려면 원장 근거·최소권종 선택·기발급 중복·부분성공·발급/사용 차이를 함께 설계해야 한다. API가 받아준다는 이유로 제한만 제거하지 않는다. 복합 부분환불은 배분 산식 확보 전 추정 구현하지 않는다.

API27은 L34에서 API25의 대안이고 API10은 기존API11 대안이 있으므로, 공개15TC 완주를 위해 반드시 추가할 기능으로 세지 않는다. 전체41API 구현을 제출의 선행조건으로 확대하지 않는다.

## 6. 담당 분리와 종료 기준

개발 담당은 [남은 개발 구상](REMAINING_DEVELOPMENT_PLAN.md)에 따라 신규 규칙 차이표와 멀티모달 설계를 진행하고, 검증 담당은 관련 모의 경계와 근거 대조를 맡는다. 화면·실API·배포 재개는 중단 상태를 존중해 별도로 조율한다. 소스 변경과 검증 결과, 미배포 후보와 운영판을 동일 상태로 기록하지 않는다.

최종 확인은 ‘필수 기대항목 증거 있음 / 미검증 / 구현 제한 / 자료 미확정’ 네 가지로 남긴다. 실패나 미검증을 모의검사 수로 상쇄하지 않고, 제출 판단 시 잔여 범위를 명시한다.
