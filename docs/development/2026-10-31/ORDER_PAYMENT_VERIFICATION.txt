2. 주문·결제 액션 검증
명세: docs/sources/action-api/actions.openapi.json 및 actions.json의 API-07/08/11/17/18, Orders/Payments/Shipments required 필드.
대상: src/order-payment-actions.mjs, src/action-context.mjs, ConversationStore.bindCase와 Worker 연결.

- 읽기 액션은 read_order, list_my_orders, read_payment, list_order_payments, list_order_shipments 다섯 개이며 GET만 사용한다.
- 공식 HTTPS 호스트·경로·TC/Authorization 헤더, redirect:manual, AbortSignal 전달을 확인했다.
- 서버 신뢰 구성에 토큰/TC/회원이 없거나 부적합하면 개인 조회 액션을 노출하지 않는다. 모델 인자로 회원·TC·토큰·URL/경로를 덮어쓸 수 없다.
- 주문 member_id 일치와 요청 대상 일치를 검사한다. 타회원 단건·혼합회원 검색 결과를 모델에 반환하지 않는다.
- 결제 단건은 연결 주문 소유를 추가 확인한다. order_no=null인 결제는 소유 확인 불가로 차단한다. 주문별 결제 검색은 소유 확인 후 호출하며 다른 주문의 결제 반환을 차단한다.
- 주소·수령인·회원 식별값·결제자명·카드 뒤4자리의 모델 반환 제외를 확인했다. 카드 정보 대사 및 미연결 결제의 완전한 업무 지원을 검증했다는 의미는 아니다.
- 필수 필드 누락·잘못된 타입/enum·추가 필드·대상 불일치·비정상 JSON은 안전한 실패 상태로 처리한다.
- 응답 64KiB 제한은 UTF-8 바이트 기준이며 거짓 Content-Length와 헤더 없는 큰 본문도 차단했다. 응답 읽기 중 취소 시 reader 취소를 확인했다.
- []/TC 오류/401/403/404/시간창429/누적429/5xx를 구분한다. 오류 본문의 임의 텍스트는 반환하지 않고 자동 재시도도 하지 않는다. beforeCall 실패 및 이미 취소된 signal은 HTTP 호출을 막는다.
- API-11 배송은 API-07 소유 확인 성공 후에만 검색한다. 모든 배송 행의 order_no 일치·필수 필드·enum·상품수량 정수·실제 유효 날짜/시간대 표기를 검증한다. delivered_location은 모델 반환에서 제외하며 빈 배열과 조회 실패·배송 성공을 혼동하지 않는다. 타회원/조회오류는 배송 검색 호출 전에 차단하고 503은 자동 재시도 없이 unavailable로 반환한다.

3. 서버 바인딩·문맥·Worker 검증
- ACTION_READ_BINDINGS는 해당 scope 해시의 정확한 TC·회원·유효 UTC 만료시각 구성만 사용한다. 누락·오류·만료·다른 scope에서는 달력만 유지한다.
- 액션 생성 후 만료되어도 외부 조회 직전에 재검사해 호출을 막는다.
- TC/회원 변경 및 바인딩 제거 시 summary와 lookup_state를 모두 비운다. 동일 바인딩 재시작에서는 기억을 유지하고 events/쓰기 기록은 삭제하지 않는다.
- 고객 메시지의 TC는 서버 바인딩 불일치를 거절할 수 있지만 인증·바인딩을 만들지 못한다.
- Worker→모델→실제 등록된 읽기 액션의 모의 HTTP→모델 도구결과→SimpleText 콜백 흐름을 확인했다. 달력 도구를 보존하고 개인정보를 제거한 결과는 도구결과 채널로 전달한다.
- 기존 integration 21개는 사용자/채팅방 격리, 중복 이벤트/쓰기, 시간만료, 저장 실패, 모델/콜백 오류 관련 기존 기능의 회귀 검증이다.

4. 합본 검증에서 발견한 기존 테스트 충돌
tests/order-lookup.test.mjs의 마지막 테스트는 /조회 TC 주문번호와 “네”만으로 주문·배송 HTTP가 2회 실행되기를 기대한다. 새 서버 바인딩 검사에서는 인증되지 않은 이 흐름을 막으므로 실제 호출 0회로 실패했다(0 !== 2).
이는 신규 읽기 모듈 30개 테스트 실패가 아니라, 다른 chat에서 병행 작성한 이전 확인 흐름의 Worker 기대값과 변경된 권한 설계의 차이다. 단순 고객 확인을 주문 귀속 인증으로 복원하여 테스트를 통과시키면 안 된다.
부모 지시에 따라 해당 테스트와 /health의 confirmed-order-status 표기, 최종 Worker/store 통합·배포는 다른 chat 담당에게 넘겼다. 이 검증 담당은 해당 소스를 추가 수정하지 않았다. 후속 로컬 전체검사에서 이전 테스트 충돌은 해소되어199/199 통과했다. 배포 chat는 제출할 최종 소스/설정 기준으로 합본·배포 검증을 수행한다.

5. 한계·남은 검증
이 검증은 실제 모델의 정책 판단 정확도, 카카오 실제 수신, p95 또는 배포 상태를 증명하지 않는다. 부모가 별도로 수행한 실제 읽기 결과는 부모 구현 기록을 따른다.
forbidden과 not_found_or_route_error 등 내부 상태 차이를 고객에게 그대로 공개하여 타인 주문 존재를 추론시키지 않아야 한다. 최종 사용자 안내의 의미·개인정보 경계는 실제 모델 검증 대상이다.
서버 바인딩의 실사용 고객 귀속 근거, 갱신/만료 절차와 운영 설정은 별도 운영 조건이다. 예시 TC·회원이나 고객이 말한 값을 인증 근거로 등록하지 않는다.
미연결 결제(order_no=null), 최소화로 제외한 카드 뒤4자리 대사, 환불·변경 접수 액션, 최종 승인·이관은 이번 읽기 검증 완료 범위가 아니다.

6. 변경 파일
이 검증 담당은 tests/action-api.test.mjs를 작성하고 이 문서를 남겼다. 원문 자료·달력 데이터·기존 병행 작업 소스와 배포는 변경하지 않았다.
