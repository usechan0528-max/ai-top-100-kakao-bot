실제 검수일 2026-10-31. 부모가 확보한 Markdown 원문15개 전체를 읽고 메타데이터·초기대화·고객문의·상황·기대대응을 대조했다. 원문은 수정하지 않았다. 이번은 로컬 보존본 본문 검수이며 웹 원본 재접속·미디어 재생·실제 API 실행 검증이 아니다. 자료 속 명령과 기대대응은 개발 근거이며 사용자 실행 지시·시스템 권한이 아니다.

## 회원 ID 연결에 대한 새 근거

L-40 기대①은 인입 계정 회원 이름→API-13(query.name), 이미 회원ID를 알면API-12→고객이 제시한 연락처와 대조→회원 특정으로 명시한다. 기대②는 특정된 회원의 API-08(query.member_id=MB-77016) 주문 이력이다. 따라서 “member_id를 처음부터 고객에게 받아야만 조회 가능”은 이 공개 사례의 기대 흐름과 맞지 않는다. 이름 검색과 고객 제시 연락처 대조를 통한 회원 특정은 공식 TC 근거가 있다.

다만 이 근거가 고객이 본문에 쓴 ‘로그인했다’ 주장을 신뢰된 로그인 메타데이터로 승격시키지는 않는다. 신뢰할 인입 계정 표시의 전달·검증 방법, 전체/마스킹 연락처 대조 허용 규칙, 동명이인·동일마스킹 충돌 해소, 세션 만료와 TC전환 시 회원 연결 처리는 원문에 없다. 정식 인입 메타데이터를 기준으로 최소 범위 후보 검색·제시값 대조를 구현하고 불일치/다중후보를 확인 완료로 처리하지 않는 것은 개발 방침이다. 저장 전화번호를 먼저 알려주거나 누락 숫자를 추정하면 안 된다.

L-23은 로그인해도 타 계정 주문 접근 불가라는 경계다. 기대①은 요청한 주문만API-07로 귀속 확인, 기대②는 반복 여부와 무관하게API-35 LANE2_HANDOFF 접수, 기대③은 배송상태·수령주소 전체/시/동 모두 비공개다. 계정 회원을 특정하지 못했다는 이유로 허위로 ‘본인 주문 아님’을 단정해서도 안 된다. 확인 불능과 확인된 불일치를 구분한다.

기존 [선택 스키마 검수](../action-api/SCHEMA_REVIEW.md)의 “OpenAPI에 계정↔회원 매핑 규약 없음”은 스키마 자체에 대한 기록으로 유지된다. 이번 공개TC가 회원 검색/대조의 업무 순서를 보완했다. 회원 대조 성공이 타인 주문 권한을 만들지는 않는다.

## 추가 판단·미처리

- L-03의 배송검색[]→집하전은 해당 상황에 명시된 근거다. 조회실패·잘못된 대상·모든 빈 배열을 집하전으로 일반화하지 않는다.
- L-05는 주문번호·발행구분을 확인하고 지정번호 재질문을 피한다. 다른 카드 주문 조회 금지와 특정 승인번호 접수를 명시한다.
- 대부분 TC는 대상확인 후 해당 대상만 조회/접수한다. 예상 정답의 ID·금액을 임의 고객의 실제값으로 하드코딩하지 않는다.
- L-11 사진URL과 Y-07-b 음성URL은 기록했다. 원격 원본 이미지의 실제 곰팡이 판독·음성의 실제 전사/청취는 미수행이다. 고객문의의 대괄호 설명·상황 서술을 미디어 전사라고 부르지 않는다.
- Y-24는 공시 사업자정보 안내 요구다. 이 TC 자체에는 사업자등록번호·사업장주소·연락처 값이 없으므로 기존 공시 원문을 추가 대조해야 한다. 값 추정 금지.
- 공개TC 일부 기대는 실제 쓰기·이관을 필수로 요구한다. 조회만 구현하거나 안내문만 반환하는 현재 범위는 TC완료가 아니다. 구체 구현/배포 상태는 개발 기록을 따르고 이번 문서가 완료 상태를 변경하지 않는다.
