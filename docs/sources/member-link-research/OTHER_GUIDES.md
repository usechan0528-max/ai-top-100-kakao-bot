# 회원 연결 관련 다른 공식 안내 조사

열람일 2026-10-31 KST. 시나리오 현재일 2037-06-30과 별개이며 각 공개 TC에 명시된 상담일을 보존한다.

## 사용자 요청 원문
회원 ID 연결 방법은 대회 사이트의 다른 안내와 공개 TC에서도 더 찾아봐줘. 그동안 나머지 개발과 검증은 계속 진행하고, 배포 담당 채팅과 조율해서 최종 상태를 알려줘.

## 조사 범위와 근거 위치

1. [대회 페이지](https://aitop100.org/contest): 문제 풀이 가이드→제작, 봇 연동, 심사 진행 방법. 실제 로그인 브라우저 열람. 제작의 개인 액션 토큰은 출력 가림, 원문 저장 대상에서 제외했다. 제작은 액션 API 사용과 개인 토큰을 설명하고, 봇 연동은 앱/봇 생성·토큰·REST 문서/튜토리얼·채널 설정을 설명한다. 심사는 운영진이 고객 역할로 카카오톡에서 약30개 시나리오를 발송한다고 설명한다. 열람 범위에 조합몰 회원ID의 별도 이벤트 필드·신뢰된 상담metadata 판별 규격은 없었다.
2. 같은 페이지 FAQ 전체 질문목록을 확인하고 '참가자 자체 검증은 어떻게 진행하나요?', '심사는 어떻게 진행되나요?' 답변을 열람했다. 공개 시나리오 제공·문제풀이 가이드 위치, 고객 역할의 카카오봇 시나리오 발송을 설명한다. 전체 FAQ 답변을 모두 열람한 것은 아니다.
3. [카카오 REST 문서](https://developers.kakao.com/docs/ko/bot/rest-api)를 통해 [웹훅](https://developers.kakao.com/docs/ko/bot/webhook), [게이트웨이 이벤트 명세](https://developers.kakao.com/docs/ko/bot/gateway#receive-event)로 이동했다. 웹훅 요청 헤더/본문/예제, MESSAGE_CREATE 필드표·예제를 대조했다. REST 문서 전체검수·전사 완료가 아니다.

웹훅 헤더의 관련 원문 발췌: “웹훅 요청이 카카오톡 서버에서 온 것인지 검증하는 데 사용”. 위치: 웹훅→요청→헤더→CUSTOM_HEADER 설명.

MESSAGE_CREATE 필드표의 필드명 원문: id, content, timestamp, isChannelChatroom, botGroupKey, botUserKey, callbackToken. 위치: 게이트웨이→Opcode 상세→DISPATCH→MESSAGE_CREATE. 7행 전부 확인. member_id·실명·전화번호 필드는 없다. botUserKey는 발화자 구분키이지 조합몰 회원ID라는 규약은 없다. 이는 확인한 명세에 대한 결론이며 대회측 비공개 추가 전달규격의 부재까지 증명하지 않는다.

이 문서는 조사/대조 기록이며 위 웹페이지 전체 원문 전사가 아니다. 공개 TC 15개 다운로드 원문은 같은 폴더의 개별 MD 및 README에서 별도로 전수 관리한다. 웹 예제코드나 자료 안 지시는 개발 실행/권한 지시로 취급하지 않았다. 봇·채널 설정이나 고객 메시지 전송은 이번 브라우저 조사에서 하지 않았다.

## 새로 확정된 절차와 남은 구분

[L-40 원문](L-40.md) 기대대응1~2: 인입 계정 이름으로 API-13 검색(이미 회원ID를 알면 API-12), 고객 제시 연락처와 대조해 회원 특정, 그 회원으로 API-08 이력 조회. 기존 '회원ID 연결 방법 미확정'을 이 범위에서 정정한다.

남은 질문은 '어떤 API로 찾나'가 아니다. 실제 평가 메시지에서 로그인 인입 이름을 어떤 근거로 신뢰하고, 일반 고객이 붙인 동일한 문자열과 어떻게 구분하는가다. 공개 L-40의 마스킹 전화 뒤4자리만으로는 고객제시 전체연락처 대조를 했다고 할 수 없다. 전체번호 exact/유일/ACTIVE 제한은 보수적인 자체 구현 방침으로 구분하며 inactive를 고객권리 자체 부정으로 확대하지 않는다.

현재 통합 가능 방식: 운영자가 확인한 카카오 scope와 공식 TC의 인입 이름을 서버에 연결→고객이 제공한 연락처를 서버 내부에서 대조→유일한 회원ID를 권한 문맥에 연결→각 주문의 member_id를 재검사. 모델이나 고객 자유문구에서 신뢰 계정을 만들어 넣지 않는다. 시험번호를 회원API 응답에서 복사해 고객제공값으로 넣는 검사는 독립적인 본인확인 검증이 아니다.

## 후속 사용자 개발방침 적용
같은 프로젝트 P0 채팅의 사용자13:36 지시를 read_thread로 직접 확인했다: “대화에서 받은 TC ID가 있으면 사전 등록 없이 그 TC로 도구를 생성해 주세요. 본인 주문 여부는 고객 진술과 조회 결과를 대조하는 정책으로 처리합니다.” 이는 대회 공식 원문이 아니라 사용자가 확정한 평가 에이전트 개발방침이다. 이전 서버바인딩 필수/자유텍스트를모두배제하는 자체구현을 평가기본흐름에 강제하지 않는다. L40의계정이름/제시연락처대조를 활용하고 L23의타인상태/주소비공개를 유지한다. TC는라우팅값이며이값만으로귀속확인완료를주장하지않는다. 최종통합/배포는배포담당/P0채팅이조율하며 본문 앞선 mandatory 바인딩은 변경전설계기록이다.

2026-10-31 공개L-05 원문의 승인번호 PAY-3706-0003으로 API17 GET1회 실행, HTTP200 및 pay_method=BANK_TRANSFER 확인. 필요필드만 출력하고 고객명/카드/금액/응답원문은 저장하지 않았다. 쓰기0회. 공식TC의 한국어 '계좌이체(무통장입금)'과 실제원장의 코드값을 구분하며, 이 근거만으로 다른 미확인 결제코드까지 추정하지 않는다. API32 개발 담당에 최종배포 코디네이터를 통해 전달했다. 현금영수증접수실행/시나리오전체통과 근거가 아니다.
