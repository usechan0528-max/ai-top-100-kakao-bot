## 3. 요약

현 코드는 오프라인 준비용 골격이다. 기존 검사는 통과하지만 실제 외부 쓰기 연결의 안전성을 보증하지 않는다.

1. **P0**: await 후 정확히 true인 경우만 실행, 쓰기 종류·실행 상태·중복 억제·불확실 잠금·시간 초과 분류. 결과 검사가 실패한 쓰기도 이미 실행됐을 수 있다.
2. **P1**: 신뢰 문맥 전달, 결과 필드 선택·값 검사·크기 제한, 안전한 오류 안내, 긴 답변 경계 보존, 서버의 콜백 단일 시도 및 불확실 결과 우선 처리.
3. **P2**: 환경 문서와 실제 실행 경로 정합성, 비밀 파일 제외 패턴, 규정과 운영 방침 구분, 기준 기록 방식.
4. **결정 대기**: 대화·중복 이벤트 상태 저장소, 요금·비용 한도, 길이 단위·전체 결과 상한, 불확실/중복 코드 우선순위 등 계약.

최신 지시서에는 이전 개발자 의견 대부분이 요구사항으로 반영됐다. 주요 차이는 문서 누락보다 **코드와 테스트 미반영**이다. 이번에는 수정하지 않았다.

별도 쟁점 판단:

1. **오류 복구 전에 쓰기 재실행 차단**이 필요하다. 현재 throw가 멈추던 경로를 history로 바꾸면 모델이 반복 실행할 기회가 생긴다. 개별 HTTP 자동 재시도 금지만으로 충분하지 않다.
2. 문맥 검증→복사/동결, 인자 검사→권한 검사→실행을 한 요청의 동일한 신뢰 경계로 묶는다. async 검사 동안 인자가 변할 수 있으므로 검사한 인자와 실행·중복 키의 인자가 같도록 확정하는 설계도 필요하다.
3. 외부 성공 뒤 pick/결과 검사 실패는 WRITE_OUTCOME_UNKNOWN과 전체 쓰기 잠금이다. “실패했으니 다시 실행”으로 반환하면 안 된다. 원본을 그대로 모델에 노출해 복구하지 않는다.
4. 전체 타이머와 fetch 중단이 경합하면 단계 상태를 먼저 확정하고 같은 실행 시도에 하나의 최종 분류를 부여한다. 전체 한도 중 쓰기 실행 중이면 TIMEOUT_DURING_WRITE, 개별 네트워크 중단이면 WRITE_OUTCOME_UNKNOWN이라는 구분과 우선순위를 계약으로 명시한다. 늦은 완료가 잠금을 풀거나 새 쓰기를 시작하게 하지 않는다.
5. 중복 키를 만들기 전 descriptor/prototype·순환·깊이·노드·지원 값 검사부터 한다. getter/toJSON을 먼저 실행하는 JSON.stringify는 피한다. 키 정렬한 안전 복사본으로 안정 직렬화하고 그 복사본을 검사/권한/실행에 일관되게 사용한다. R은 결과 검사만 상세하므로 **인자 허용 값과 실패 코드**는 추가 계약이 필요하다.
6. R:150은 결과 직렬화 상한, :157은 history 해당 항목 전체 상한처럼 읽힌다. name/source/truncated/preview·JSON escape 오버헤드 포함 여부와 상한 단위가 불명확하다. 제안은 전체 history 항목의 직렬화 크기에 메타데이터까지 포함하고, 답변은 별도 한도로 명시하는 것이다. UTF-16/code point/자소/UTF-8 바이트 중 단위를 확정하고 절단 경계는 자소를 우선한다. 메타데이터보다 작은 설정은 설정 오류로 거부한다.
7. 기본 minWriteBudgetMs=3000인 채 timeoutMs=5 테스트를 쓰면 execute 전에 막혀 쓰기 중 시간 초과를 검증하지 못한다. 예산 거부 테스트와 실행 중 timeout 테스트를 분리하고, 후자는 테스트용 예산을 명시적으로 낮추며 단계 진입 barrier로 실제 쓰기 시작을 확인한다.
8. A 쓰기 성공 후 B 실패/불확실, 또는 후속 모델 실패일 때 A의 성공을 잃지 않는 정리된 작업 요약이 필요하다. outcomeUnknown만으로 “무엇이 완료됐는지”는 부족하다. 오류 객체에도 비밀 없는 누적 상태를 보존할지 결정해야 한다.
9. 모델의 성공 문구보다 outcomeUnknown 및 신뢰 가능한 실행 기록을 서버가 우선해야 한다. 불확실 고정 안내로 대체하거나 검증된 작업 요약과 함께 보내야 하며 성공 문구를 그대로 전달하지 않는다.
10. Git 없는 기준은 파일 해시와 관찰 시간으로 식별한다. OneDrive 상태는 추정하지 않고 재해시 차이를 기록한다. 미래 구현자는 별도 승인 하에 기준 기록·동기화 충돌 대책을 마련한다.

추가 기준 모호함: R:112의 같은 쓰기 중복 거부와 :126의 불확실 뒤 동일 쓰기 WRITE_LOCKED가 겹친다. 제안은 불확실 잠금을 우선 적용하고, 잠금 없는 중복은 DUPLICATE_WRITE로 하는 것이다. ACTION_NOT_EXECUTED로 확정 거부된 동일 쓰기도 “한 번 시도” 기록에 포함할지 명시해야 한다. R:99의 kind 오타를 쓰기로 취급하는 안전 기본값은 유지하되 도구 등록 단계 진단을 제안한다.

## 7. 서버 통합 요청

별도 서버 파일을 읽거나 바꾸지 않았고 다른 대화에 메시지를 보내지 않았다. 다음은 총괄자가 별도 대화에 전달할 요청 내용이다(REVIEW_TASKS.md:164~178).

- 에이전트 오류를 userMessageFor 같은 안전한 안내로 변환하고 이벤트당 콜백 시도 상태를 관리한다. 정상 답변 콜백을 이미 시도했다면 실패 뒤 오류 콜백을 추가하지 않는다.
- 콜백 실패·시간 초과는 에이전트 재실행 사유로 삼지 않는다. 전달 불명 시 자동 재전송하지 않고 원문·토큰 없는 최소 운영 정보만 남긴다.
- outcomeUnknown이 true면 모델의 성공 문구보다 우선하여 불확실 안내를 보낸다. 이후 예외에도 이미 성공한 작업과 미확인 작업을 구분할 수 있는 계약이 필요하다.
- 인증된 이벤트의 사용자·채널·이벤트 식별자를 신뢰 문맥으로 전달한다. 모델 arguments의 식별자는 신뢰하지 않는다.
- 이벤트 ID 중복 방지·동시 처리 원자성·사용자별 요청 한도와 상태 보존 기간을 정한다. 이벤트 단위 중복과 새 이벤트의 같은 작업 중복은 별개다.
- 에이전트+콜백 전체 시간 예산, 웹훅 비밀 비교 방식을 검토한다. 문서의 12+15=27초는 산술상 합계일 뿐 공식 허용 한도나 현재 서버 설정의 직접 검증이 아니다.

공식 재확인 대상: 카카오 이벤트 식별자/인증/재전달·콜백 토큰 유효 기간·응답 길이 단위·전송 제한, Cloudflare waitUntil의 실제 상품/실행 방식별 한도와 수명, 대회 API의 메서드·주소·인증·성공/미실행 의미·멱등 키·상태 조회 지원. README:59~63과 개발 문서:140도 공식 전송 규격 미확인을 밝힌다. 별도 worker 추가 열람은 현재 보고서에 필요하지 않았으며 통합 구현 검토 때 별도 범위로 요청해야 한다.
